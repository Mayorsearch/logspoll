# Workers + D1 migration — isolated staging foundation

Existing Pages, Supabase, frontend, payment/supplier Functions and DNS remain unchanged. The separate `workers/api` Worker is a **read-only synthetic staging API**, not a completed platform migration or authentication replacement. Eventually route `/api/*` on the same website origin to this Worker; that avoids cross-origin cookies/CORS. Do not add the domain route until the full migration passes and domain cutover is approved. No R2 bucket is necessary for stored public image URLs.

`workers/api/wrangler.jsonc` contains independent staging and locked production environments. Production has no database binding, route, hostname or active handler. No production credentials were copied. The user confirmed Workers/D1 are on the Free plan; no paid plan upgrade was requested. Cron has **no triggers** in this new Worker. Existing scheduler flags stay unchanged/off.

## Commands (staging only)

```sh
python3 scripts/verify-d1-staging.py
npx wrangler d1 migrations apply DB --config workers/api/wrangler.jsonc --env staging --local
npx wrangler d1 execute DB --config workers/api/wrangler.jsonc --env staging --local --file workers/api/fixtures.sql
npx wrangler dev --config workers/api/wrangler.jsonc --env staging --local
```

Remote creation/migrations/deployment target the dedicated staging name only. Before a future import, export a **staging** backup using `wrangler d1 export DB --config workers/api/wrangler.jsonc --env staging --remote --output /private/tmp/logspoll-staging-backup.sql`. Verify the backup contains only synthetic data. Apply reviewed migrations with `d1 migrations apply ... --remote`; use `npx wrangler d1 execute DB --config workers/api/wrangler.jsonc --env staging --remote --command="$(cat workers/api/verify.sql)" --json` for counts, integer-price/stock checks, FK/quick-check and marker verification. D1 supports `PRAGMA quick_check`, not SQLite’s full `integrity_check`; see [supported statements](https://developers.cloudflare.com/d1/sql-api/sql-statements/). Wrangler records migrations; fixture inserts do not replace existing values. Production customer import/export scripts are intentionally not prepared as runnable shortcuts before approval and full schema compatibility.

Rollback requires no production change: keep the existing Pages/Supabase application authoritative and leave the new staging Worker unreferenced. Keep additive D1 staging data; do not delete databases or downgrade schemas automatically. A restore should target a new isolated staging database, followed by count/hash/price/stock and FK verification, before rebinding. Never use restore to overwrite production.
